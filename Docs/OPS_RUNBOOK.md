## 1. CI/CD Pipeline Overview

### 1.1 GitHub Actions Workflow

**File:** `.github/workflows/ci.yml`

**Triggers:**
- **Push to `main`:** Full CI suite runs on every merge
- **Pull Requests:** CI runs on all PRs before merge approval
- **Daily Schedule:** 6:00 AM UTC cron job (nightly regression)
- **Manual Dispatch:** On-demand via GitHub Actions UI

**Pipeline Stages:**

```
┌─────────────────┐
│ 1. Checkout     │
│    Repository   │
└────────┬────────┘
         ▼
┌─────────────────┐
│ 2. Setup Node   │
│    (v20 LTS)    │
└────────┬────────┘
         ▼
┌─────────────────┐
│ 3. npm ci       │
│    (web/)       │
└────────┬────────┘
         ▼
┌─────────────────┐
│ 4. Lint Check   │
│    (ESLint)     │
└────────┬────────┘
         ▼
┌─────────────────┐
│ 5. Unit Tests   │
│    (Vitest)     │
└────────┬────────┘
         ▼
┌─────────────────┐
│ 6. Install      │
│    Playwright   │
└────────┬────────┘
         ▼
┌─────────────────┐
│ 7. Visual Tests │
│    (Playwright) │
└────────┬────────┘
         ▼
┌─────────────────┐
│ 8. Upload       │
│    Artifacts    │
└─────────────────┘
```

**Artifacts Generated:**
- `playwright-report` — HTML test report (always uploaded, even on failure)
- `playwright-traces` — Trace files for debugging failures (always uploaded)

**Typical Runtime:** 3-5 minutes

### 1.2 Branch Protection Rules

**Required Checks for `main`:**
- ✅ All CI tests pass (lint, unit, visual)
- ✅ At least 1 approving review
- ✅ No merge conflicts
- ✅ Branch up to date with `main`

**Recommended (Not Yet Enforced):**
- ⏳ Data validation (`npm run validate:data`) — TODO: Add to CI
- ⏳ Build succeeds (`npm run build`) — TODO: Add to CI
- ⏳ Migration smoke test — TODO: Add to CI

### 1.3 Adding New CI Checks

**Template for extending `.github/workflows/ci.yml`:**

```yaml
- name: Run data validation
  run: npm run validate:data

- name: Build production bundle
  run: npm run build

- name: Check bundle size
  run: |
    BUNDLE_SIZE=$(du -k web/dist/assets/*.js | awk '{total += $1} END {print total}')
    if [ $BUNDLE_SIZE -gt 10240 ]; then
      echo "Bundle size ${BUNDLE_SIZE}KB exceeds 10MB limit"
      exit 1
    fi
```

**Steps to Add:**
1. Edit `.github/workflows/ci.yml`
2. Add step in appropriate sequence (after dependencies installed)
3. Test locally: `npm run <script-name>`
4. Open PR with CI changes
5. Verify new check appears in GitHub PR status

## 2. Deployment Procedures

### 2.1 PWA Deployment Architecture

**Hosting:** (To be determined — currently local development only)
**Expected Stack:**
- Static hosting (Netlify, Vercel, Cloudflare Pages, or GitHub Pages)
- Service Worker for offline caching
- IndexedDB for save persistence

**Build Output:** `web/dist/` (generated by `npm run build`)

### 2.2 Pre-Deployment Checklist

**Before every deployment:**

- [ ] All CI checks pass on `main` branch
- [ ] Service worker version bumped in `web/src/service-worker.ts`
- [ ] Save schema migrations tested (see §2.4)
- [ ] Release notes drafted in `/Docs/releases/<phase>.md`
- [ ] Lighthouse audit run (target: ≥90 Performance, ≥90 Accessibility)
- [ ] Offline/install flows smoke tested on Chrome desktop + Safari iOS

**Phase-specific:**
- [ ] **Homestead:** 30-day soak test passed
- [ ] **Township:** Homestead→Township export validated with 5 legacy saves
- [ ] **Nation:** Township→Nation converter smoke test
- [ ] **Stellar:** NG+ seed generator verified

### 2.3 Service Worker Cache Invalidation

**File:** `web/src/service-worker.ts`

**Version Format:** `v<schemaVersion>-<build-date>` (e.g., `v7-2025-11-09`)

**Update Protocol:**
1. Increment cache version constant:
   ```ts
   const CACHE_VERSION = 'v7-2025-11-09'; // Update this line
   ```
2. Service worker auto-updates clients on next page load
3. Old caches purged via `caches.delete(oldCache)`

**Testing:**
1. Build with new version: `npm run build`
2. Serve locally: `npm run preview`
3. Open DevTools → Application → Service Workers
4. Verify new version active after refresh
5. Check Cache Storage shows updated version

### 2.4 Save Migration Sign-Off

**Required Before Deployment:**

1. **Load 5 legacy saves** (one from each previous schema version):
   ```bash
   cd web
   npm run migrate -- --file ../fixtures/v0-legacy.json
   npm run migrate -- --file ../fixtures/v1-legacy.json
   # ... repeat for v2-v6
   ```

2. **Verify migration success:**
   - No console errors
   - Game loads without crashes
   - Resources/buildings/state preserved
   - No NaN or undefined values in critical state

3. **QA Sign-Off:**
   - Engineering approves migration logic
   - QA confirms in-game state matches expectations
   - Producer acknowledges user data risk assessment

**Rollback Plan:** If migrations fail post-deployment, see §7.2

## 3. Incident Response Playbook

### 3.1 Severity Definitions

| Severity | Definition | Response Time | Examples |
|----------|-----------|---------------|----------|
| **Sev-1** | Game unplayable or data loss | **15 min** | Saves corrupted, white screen on load, service worker crash loop |
| **Sev-2** | Major feature broken | **4 hours** | Build mode non-functional, economy system frozen, audio completely silent |
| **Sev-3** | Minor bug, workaround exists | **3 days** | Visual glitch, typo in quest text, balance issue |
| **Sev-4** | Polish/nice-to-have | **Next sprint** | HUD alignment, color tweak, performance micro-optimization |

### 3.2 Sev-1 Incident Response

**Immediate Actions (First 15 Minutes):**

1. **Alert Stakeholders:**
   - Post in #incidents Slack channel: `@engineering-lead @producer SEV-1: [brief description]`
   - Create incident ticket in bug tracker
   - Start incident timer (track MTTR — Mean Time To Resolve)

2. **Assess Scope:**
   - Affected users: All? Subset? (check telemetry dashboard if available)
   - Reproducible: Always? Intermittent?
   - Data loss risk: Are saves being corrupted?

3. **Containment:**
   - If PWA deployed: Initiate emergency rollback (see §7.1)
   - If pre-deployment: Block merge to `main`
   - Disable feature flags if applicable

**Resolution Actions (Next 2 Hours):**

4. **Root Cause Analysis:**
   - Review error logs (browser console, telemetry errors)
   - Check recent commits: `git log --oneline -10`
   - Reproduce locally: `npm run dev`, follow user steps

5. **Fix or Revert:**
   - **Hot fix:** If 1-line code change, PR with `[SEV-1]` prefix
   - **Revert:** If complex, revert offending commit: `git revert <sha>`
   - Fast-track review: Engineering Lead approval sufficient

6. **Deploy Fix:**
   - CI must pass (no skipping tests, even in emergencies)
   - Deploy via standard process (see §2.2)
   - Monitor telemetry for 1 hour post-deploy

**Post-Incident (Within 24 Hours):**

7. **Document Timeline:**
   - Add entry to `Docs/BUG_TRIAGE.md` with:
     - Detection time, response time, resolution time
     - Root cause, fix applied, users affected
     - Prevention measures (e.g., "Add migration test for edge case")

8. **Retro Meeting:**
   - Invite: Engineering Lead, QA Lead, Producer
   - Discuss: What went wrong? How to prevent? What to improve?
   - Action items tracked in backlog

### 3.3 CI Downtime Response

**If GitHub Actions Fails:**

1. **Check GitHub Status:** https://www.githubstatus.com
   - If GitHub outage: Wait, notify team, reschedule merges

2. **If Internal Issue:**
   - Review workflow run logs in GitHub Actions UI
   - Common causes:
     - Dependency installation timeout → Retry
     - Playwright browser install failure → Clear cache, retry
     - Flaky test → Isolate test, mark as `@flaky`, investigate

3. **Temporary Bypass (Emergency Only):**
   - Admins can override branch protection (requires approval)
   - **Never bypass for convenience** — only for Sev-1 fixes with verified local CI pass

**On-Call Rotation:** (To be established in Township phase)

### 6.2 Data Loss Scenarios

**If User Reports Save Corruption:**

1. **Collect Debug Info:**
   - Browser version, OS, last known good save timestamp
   - Console errors (ask user to open DevTools → Console, screenshot)
   - Save file export: `localStorage.getItem('farmToStars:save')`

2. **Attempt Recovery:**
   - Check migration path: Does save have valid `schemaVersion`?
   - Load in dev environment: `npm run dev`, paste save JSON
   - If migration fails: File Sev-1, investigate schema mismatch

3. **User Mitigation:**
   - If save unrecoverable: Apologize, offer to manually construct equivalent save
   - If pattern detected: Emergency patch + public communication

**Prevention:**
- Regular downgrade fixture testing (see §2.4)
- Save versioning ensures backward compatibility
- Local backups encouraged (future: auto-export feature)

### 6.3 Service Worker Crash Loop

**Symptoms:** App won't load, stuck on loading screen, console shows repeated SW registration failures

**Fix:**
1. **User Self-Service:**
   - Clear site data: DevTools → Application → Clear storage
   - Hard refresh: Ctrl+Shift+R (Windows) / Cmd+Shift+R (Mac)

2. **Developer Fix:**
   - Identify faulty SW version: Check `web/src/service-worker.ts` in broken commit
   - Deploy hotfix with corrected SW
   - Communicate fix timeline to users (e.g., Twitter, Discord announcement)

3. **Prevention:**
   - Test SW offline/install flows before every deploy (see §2.2 checklist)
   - Add SW smoke test to CI (future)

## 7. Rollback Protocols

### 7.1 Emergency Rollback (PWA Deployment)

**When to Rollback:**
- Sev-1 issue detected in production
- Fix ETA > 2 hours
- User data at risk

**Procedure:**

1. **Identify Last Known Good (LKG) Commit:**
   ```bash
   git log --oneline -20  # Review recent commits
   # Find last commit before issue introduced
   ```

2. **Deploy LKG:**
   - Checkout LKG commit: `git checkout <lkg-sha>`
   - Build: `npm run build`
   - Deploy via hosting platform (Netlify/Vercel/etc.)
   - Verify SW cache version differs from broken version

3. **Communicate:**
   - Post in #announcements: "We've rolled back to [version]. Refresh your browser."
   - Twitter/Discord: Brief apology + ETA for fix

4. **Post-Rollback:**
   - Investigation continues on broken commit
   - Fix developed on feature branch
   - Full CI + manual QA before re-deploy

### 7.2 Save Migration Rollback

**Problem:** New schema version (e.g., v8) breaks saves, users can't load games

**Immediate Fix:**
- Deploy LKG with previous schema version (e.g., v7)
- Users' saves remain compatible

**Long-Term Fix:**
1. Review migration logic in `web/src/migrations.ts`
2. Add test cases for broken scenario
3. Fix migration, add downgrade path if needed
4. Re-deploy after QA sign-off

**Data Recovery:**
- If saves already migrated to v8: Provide manual downgrade script
- Communicate instructions to affected users
